# 15 — «Сценарии»: правила, наполняющие очередь

**Закрыт 2026-08-25.** Ядро продукта: система впервые решает сама, кого коснуться.

## Что теперь верно

`/ru/scenarios` — правила с мерой пользы, создание, выключатель, сведение с людьми и запуск.
Четыре двери: `GET/POST /api/care/scenarios`, `PATCH /api/care/scenarios/[id]`,
`GET/POST /api/care/scenarios/[id]/run`.

**Живая проверка:** правило «не был больше 60 дней» нашло **94 человека** и завело 94 задачи.
Независимый контрольный запрос к базе даёт те же **94**.

## Два закона, взятые из исходника дословно

1. **🔒 ПРАВО АСИММЕТРИЧНО.** Список видит весь персонал; создать, изменить или запустить правило может
   ТОЛЬКО администратор. Сценарий решает, кому уйдут сообщения: видеть правило и менять его — разные
   способности. Оператор, работающий по очереди, не должен уметь переписать правило, которое эту
   очередь порождает.
2. **🔒 ПРАВИЛО ПОКАЗЫВАЕТ СВОЮ ПОЛЬЗУ ЧИСЛОМ.** У каждого стоит «породило задач», «из них записались»,
   «открыто сейчас» и доля. Без них правило невозможно оценить: оно либо возвращает людей, либо гоняет
   их впустую. **Правило без меры живёт вечно, потому что никто не видит, что оно не работает.**

## 🔴 Дефект исходника, который мы НЕ повторяем

**Генерация Филиппа отбирает людей по колонкам `last_visit_date` / `next_visit_date`** таблицы
пациентов. Его же собственный код в другом месте документирует, что эти колонки **заполнены у
меньшинства карточек**.

Правило, построенное на них, молча пропустило бы большинство тех, кого должно найти — и никто бы этого
не заметил: **пустая выборка выглядит как «подходящих нет»**. Здесь факты о визитах считаются из
`care_visits`, как велит закон шага 10.

## Второе расхождение с исходником, названное вслух

**Генерация по сценариям в исходнике имела ДВА предохранителя** (согласие, открытая задача) и обходила
третий — «касались недавно», который стоял только в массовом создании с экрана.

Похоже на недосмотр, а не решение: правило, срабатывающее каждый день, без остывания пишет человеку
каждый день. **Здесь запуск идёт через `createTasks` шага 14, то есть со всеми тремя.** Решение моё,
названо здесь; Рома поправит, если считает иначе.

## Решения, принятые в этом шаге

1. **Удаления у правил нет намеренно — только выключатель.** Выключенное правило остаётся видно вместе
   с мерой: «породило 340 задач, из них 12 записей» — это знание, и стирать его вместе со строкой
   значит терять единственное основание судить, стоило ли правило заводить.
2. **Мёртвый триггер помечен, но не запрещён.** `birthday` не выстрелит (шаг 13), и это сказано и в
   форме, и на карточке, и в ответе двери. Запрещать нельзя — данные могут появиться; молчать нельзя —
   владелец заведёт правило и будет ждать месяцами.
3. **Направление сужает по РЕАЛЬНО оказанным услугам**, а не по `care_cases.service_direction`:
   колонка пуста у всех, CRM её не отдаёт. Фильтр по ней дал бы пустую выборку и вывод «подходящих
   нет».
4. **Доля «доходит до записи» не показывается при нуле задач.** 0/0 — это «судить не по чему», а не
   «0%»: показать ноль процентов значило бы обвинить правило в бесполезности, которую никто не
   проверял.
5. **Два триггера сводятся вручную** (`manual_segment`, `unfinished_treatment`) — как в исходнике.
   Кнопка запуска у них не рисуется, причина названа словами.

## Доказательство первое — двери на живых данных

    ① создание рабочего правила          HTTP 200  id sc-3BMVz6
    ② создание на МЁРТВОМ триггере       HTTP 200 + warning «нет данных на филиале»
    ③ без цели контакта                  HTTP 400  «укажите цель контакта»
    ④ выдуманный триггер                 HTTP 400  «неизвестный тип триггера»
    ⑤ отрицательный порог                HTTP 400  «порог от 0 до 3650»
    ⑥ выключатель                        HTTP 200  changed ["isActive"]
    ⑦ небывалый сценарий                 HTTP 404

**Каждый негативный контроль называет СВОЮ причину** — общий отказ не дал бы отличить незаполненное
поле от выдуманного значения.

## Доказательство второе — сведение и запуск

    ① выключенное правило: GET считает 94, POST → HTTP 409 «правило выключено»
    ② включили и запустили: candidates 94, created 94, отсеяно 0
    ③ ПОВТОРНЫЙ запуск:    candidates 94, created 0, hasOpenTask 94
    ④ мёртвый birthday:    candidates 0, noData true
    ⑤ небывалый сценарий:  HTTP 404

    сверка с базой: задач всего 97, по сценарию 94
    независимый контрольный запрос «не был >60 дней и не записан вперёд» → 94

**Что доказывает:** число, найденное правилом, сошлось с числом, посчитанным независимым запросом, и
предохранители отсекли ровно тех же 94 при повторе. **Как выглядело бы без правки дефекта исходника:**
выборка по колонкам дела дала бы горстку вместо 94 — и это выглядело бы как «подходящих почти нет».

Гейты: **17 из 17 зелёные**, `check:types` и `check:i18n` зелёные.
