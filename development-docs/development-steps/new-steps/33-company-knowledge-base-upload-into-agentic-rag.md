# 33 — База знаний компании: загрузка документов в агентный RAG

**Заказ Ромы 2026-08-25.** «В этой же вкладке внизу добавим инструмент для загрузки в агентный RAG
данных компании, которые будут составлять базу знаний компании. Так же, как реализовано в панели
управления: запускается процесс, который векторизует… создаёт граф связей с этими документами, чтобы
потом пользователь мог этой информацией пользоваться нативно. Документов может быть несколько».

## Проверено до плана — ничего строить с нуля не нужно

**Помощник УЖЕ НАПИСАН** — `lib/fractera/knowledge.ts`, четыре функции:

    ask                 спросить у графа
    learn(text, source) отдать документ на изучение
    knowledgeDocuments  что движок уже держит
    knowledgeReady      жив ли он

**Движок отвечает** — запрос с сервера к `/service/rag/documents` вернул `200`.

🔒 **КЛЮЧА ДВИЖКА У НАС НЕТ И НЕ ДОЛЖНО БЫТЬ.** Обращение идёт через слой данных, который сам
подставляет ключ на петле сервера; движок в интернет не опубликован. Поэтому никакого нового поля в
блоке ключей для RAG не появится — и это правильно.

## 🔒 ТРИ ЗАКОНА ИЗ НАВЫКА, КОТОРЫЕ ОПРЕДЕЛЯЮТ ВЕСЬ ИНТЕРФЕЙС

**① ЗАГРУЗКА ДОРОГА, ВОПРОС ДЁШЕВ.** `learn` заставляет модель прочитать КАЖДЫЙ кусок документа,
чтобы вытащить сущности и связи. Это главная статья расхода всей возможности.
**Следствие для экрана:** он обязан сказать цену ДО запуска, а не после. «Загрузить весь архив на
всякий случай» — вот как эта возможность становится дорогой, не становясь полезной.

**② ГРАФ СТРОИТСЯ В ФОНЕ.** `learn` возвращается, как только документ ПРИНЯТ. Спроси через секунду —
честный ответ будет «ничего не найдено», потому что граф ещё строится.
**Следствие:** экран показывает СОСТОЯНИЕ ОБРАБОТКИ, а не «готово» сразу после загрузки. Иначе
администратор задаст вопрос, получит пустоту и решит, что загрузка не удалась.

**③ УДАЛЕНИЕ АСИНХРОННО, И `200` НЕ ДОКАЗАТЕЛЬСТВО.** Движок отвечает «удаление начато».
**Следствие:** после удаления список перечитывается, а не правится на экране.
И удалять только ПО ИДЕНТИФИКАТОРУ документа, не по имени: имя набрал человек, идентификатор выдал
движок.

## Подшаги

**33-1 — чтение состояния.** Дверь отдаёт список документов движка и его готовность.
*Пруф:* список совпадает с прямым запросом к `/service/rag/documents`; гость `401`.

**33-2 — загрузка.** Файл → текст → `learn`. Несколько файлов за раз, каждый отдельным документом
(его имя и есть `source`).
🔒 **ИЗВЛЕЧЕНИЕ ТЕКСТА — ОТДЕЛЬНЫЙ ВОПРОС ДЛЯ PDF И DOCX.** Простой текст и markdown читаются как
есть; для двух других нужна разборка, и в проекте её нет. Чего не умеем — не принимаем: список
допустимых типов сузится до того, что действительно читается, а не до того, что красиво выглядит в
подсказке.
*Пруф:* документ появился в списке движка; негативный контроль — файл неподдерживаемого типа
отклонён с внятным словом.

**33-3 — состояние обработки.** Опрос `pipeline_status`, пока документ не в графе.
*Пруф:* сразу после загрузки состояние «обрабатывается», позже — «в графе».

**33-4 — удаление.** По идентификатору, с перечитыванием списка.

## Что НЕ делать

① не обещать «готово» сразу после загрузки — граф строится в фоне;
② не удалять по имени;
③ не принимать типы файлов, которые не умеем читать;
④ не молчать о цене загрузки;
⑤ не заводить ключ RAG в настройках — его подставляет слой данных.

## 🔒 РЕШЕНИЕ РОМЫ 2026-08-25: ТОЛЬКО ТЕКСТ И MARKDOWN

Дословно: «text и md. Для работы с другими форматами требую, чтобы люди использовали конвертер,
который доступен в открытом доступе на сайтах в интернете, чтобы преобразовать в наш формат;
рекомендован Markdown».

**Это делает шаг втрое короче и честнее.** Разборки PDF и DOCX в проекте нет; приняв их, мы клали бы
в граф мусор из служебной разметки — и узнали бы об этом по кривым ответам модели, а не по ошибке.

🔒 **ОТКАЗ ОБЯЗАН ОБЪЯСНЯТЬ, А НЕ ПРОСТО ОТКАЗЫВАТЬ.** Человек, принёсший .docx, должен прочитать на
экране, ЧТО делать: перевести в Markdown любым конвертером и принести снова. Отказ без выхода
читается как поломка.
